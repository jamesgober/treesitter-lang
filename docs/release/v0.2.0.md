# treesitter-lang v0.2.0 — Tree-sitter Grammars from Rust

**The core, and the hard part of the roadmap.** v0.2.0 turns the scaffold
into a working tree-sitter grammar generator: describe a language's syntax
with rules in Rust, and emit the `grammar.js` or `grammar.json` that
`tree-sitter generate` turns into a parser. Grammars are validated against
the rules tree-sitter itself enforces before anything is written, the two
output formats generate the same parser, and the trees a language's hand-written
parser builds render as tree-sitter corpus tests, so the generated parser can
be held to the real one. The surface is three types, and the crate depends on
`syntax-lang` alone.

## What is treesitter-lang?

The bridge between a language built with the `-lang` family and the editor
ecosystem built on tree-sitter. Such a language already has a hand-written
parser producing lossless `syntax-lang` trees; editors want a tree-sitter
grammar for highlighting, folding, and navigation. treesitter-lang lets that
grammar be written in Rust next to the parser, generated from the same
tables, checked before tree-sitter runs, and tested against the parser it
must agree with. It is one of the FEAT-tier crates of the `-lang`
language-construction family.

## What's new in 0.2.0

### `Rule` — tree-sitter's rule language

Each constructor is one function of tree-sitter's `grammar.js` DSL and is
emitted as that function: `symbol`, `string`, `pattern`, `blank`, `seq`,
`choice`, `optional`, `repeat`, `repeat1`, `field`, `alias`, `token`,
`immediate`, `prec`, `prec_left`, `prec_right`, `prec_dynamic`. Rules are
plain values — build them in loops, keep them in variables, clone shared
pieces — and text arguments take `impl Into<Cow<'static, str>>`, so literals
are stored without copying and names built at run time are taken as they are.

```rust
let e = || Rule::symbol("_expression");
let table = [("+", 1), ("-", 1), ("*", 2), ("/", 2)];
let binary = Rule::choice(table.map(|(op, level)| {
    Rule::prec_left(level, Rule::seq([e(), Rule::string(op), e()]))
}));
```

### `Grammar` — build, validate, emit

A grammar is a name, an ordered list of rules (the first is the start rule),
and tree-sitter's grammar-level settings: `extra`, `external`, `supertype`,
`inline`, `conflict`, and `word`. `to_js` emits `grammar.js` laid out the way
grammars are written by hand; `to_json` emits `grammar.json`. The `write_`
forms append to a caller's buffer and leave it untouched on error.

```rust
let js = Grammar::new("calc")
    .extra(Rule::pattern(r"\s"))
    .rule("source_file", Rule::repeat(e()))
    .rule("_expression", Rule::choice([Rule::symbol("number"), Rule::symbol("binary")]))
    .rule("binary", binary)
    .rule("number", Rule::pattern(r"\d+"))
    .to_js()?;
```

Generating from either format produces the same `parser.c`. With
tree-sitter 0.25 or later, the emitted `grammar.json` is also byte-identical
to the `src/grammar.json` tree-sitter writes when it generates from the
emitted `grammar.js` — same `$schema` line, field order, and layout, with
patterns recorded as they appear between the slashes. Checked against
tree-sitter 0.20.8, 0.22.6, 0.24.7, 0.25.10, 0.26.3, and 0.27.0: all of them
load the emitted `grammar.json`; 0.24 through 0.27 generate the same parser
from both formats (0.20 and 0.22 were not run on `grammar.js`); and 0.24
differs from ours only by the final, empty `reserved` field.

### Validation that mirrors tree-sitter

Emission validates first and returns the first problem as an `Error`, from
fifteen documented variants. Some checks apply to every rule, because
`grammar.js` evaluates every rule: identifier names, a visible start rule, no
duplicates, symbols that resolve (in rules, extras, `word`, `conflicts`,
`inline`, and `supertypes`), no empty patterns or choices, no symbols inside
tokens. The rest apply to the rules reachable from the start rule and the
extras, because tree-sitter drops the others before building the parser: no
empty strings, no referenced rule or repetition that can match the empty
string, no cycle of rules that are each just the next, and word, external,
inline, and supertype declarations tree-sitter can honour.

Those last depend on which rules tree-sitter turns into tokens, and its rules
for that are subtle: it merges identical tokens (`token('x')` is the same as
`'x'`), so a word rule whose token appears elsewhere stops being a token; a
hidden rule whose token is a bare string is that anonymous string, not a
token; and supertypes count as hidden. Every one of these was probed against
the tree-sitter 0.27 CLI before it was written down. Three grammars that make
tree-sitter crash or hang instead of reporting an error — a nullable extra
rule, recursion through inlined rules, and a hidden rule that is itself under
a precedence — are refused as errors.

```rust
let grammar = Grammar::new("demo")
    .rule("source_file", Rule::repeat(Rule::symbol("block")))
    .rule("block", Rule::seq([Rule::string("{"), Rule::symbol("body"), Rule::string("}")]))
    .rule("body", Rule::repeat(Rule::symbol("statement")))
    .rule("statement", Rule::seq([Rule::pattern("[a-z]+"), Rule::string(";")]));

assert_eq!(grammar.to_js(), Err(Error::MatchesEmpty { rule: "body".into() }));
```

Before this release, an adversarial review attacked the crate's claims with
hand-built grammars, and a differential fuzzer generated more than ten
thousand random grammars and ran each through both validation and
`tree-sitter generate`. Every disagreement the two turned up was traced to its
cause in tree-sitter and fixed — the reachability rule, the token rules
above, the supertype and inline rules, the hangs, duplicate `inline` entries
(now written once, as tree-sitter keeps them), control characters in patterns
(now escaped), and an empty `seq()` inside a token (now emitted as
`blank()`). On the final code, the fuzzer found no grammar validation accepts
that tree-sitter refuses, and none it refuses that tree-sitter accepts, beyond
the documented stricter checks: an empty `choice`, an `inline` entry
naming no rule, and empty patterns and empty strings inside tokens.

### `Grammar::sexp` — corpus tests from your own parser

`sexp` renders a `syntax_lang::Node` as the S-expression tree-sitter prints
for the same input: hidden, inlined, and supertype rules spliced, rules that
lex a single token as leaves, rules that name no other node showing only the
extras inside them, alias names recognized, externals shown unless hidden,
anonymous tokens left out, two-space indentation per level. Name the parser's kinds after the grammar's rules,
render its trees, and write them as corpus entries; `tree-sitter test` then
checks the generated parser against the hand-written one.

```rust
let mut corpus = String::from("==========\nSum\n==========\n\n1 + 2\n\n---\n\n");
grammar.write_sexp(&tree, Kind::name, &mut corpus)?;
// (source_file
//   (sum
//     (number)
//     (number)))
```

### Examples

Three runnable examples ship. `calc` builds a calculator grammar, prints it,
and shows validation catching a mistake. `generate` and `corpus` share
`mini`, a small expression language set up as a real `-lang` language would
be: its grammar built from the same operator table its hand-written Pratt
parser uses, and a parser that places comments where tree-sitter places
extras. `generate` writes its `grammar.js` and `grammar.json`; `corpus` parses
six samples and writes them as a tree-sitter corpus, which passes
`tree-sitter test` against the generated parser.

### Tests and conformance

Every public item has rustdoc with runnable examples, and every `rust`
example in `README.md` and `docs/API.md` runs as a doctest. The property
tests emit random rule trees — with strings full of quotes, backslashes,
control characters, U+2028, and arbitrary Unicode — in both formats and read
them back with independent `grammar.js` and `grammar.json` parsers written in
the test; they must come back unchanged. Further properties check the
empty-match rule, repetitions included, against a direct recursive
definition, and `sexp` against a reference renderer covering hidden,
inlined, supertype, token, alias, and extra names. A soak of 100,000 cases
per property found nothing.

A new `tree-sitter` CI job installs the tree-sitter CLI and runs
`dev/conformance.sh` over a grammar exercising every rule type and setting,
the `mini` grammar and corpus, and a minimal grammar: generation must
succeed, `grammar.json` must match tree-sitter's byte for byte, both formats
must generate the same parser, and the corpus must pass.

### Dependency wiring

`syntax-lang` 1 is wired and re-exported whole: `Grammar::sexp` reads its
`Node`, and callers build trees with the same version. The CST records what
was parsed, not the rules that allow it, so the grammar is not inferred from
it; it is written in Rust and held to the parser by corpus tests. The
reasoning is recorded in `dev/ROADMAP.md` under the anti-deferral rule. The
scaffold's unused `serde` feature and `loom` dev-dependency were removed.

### Scaffold fixes

`Cargo.toml` had unquoted `keywords` and `categories`, so the manifest did
not parse at all; `clippy.toml` declared MSRV 1.87 against the crate's 1.85;
`deny.toml` named another project; two docs carried byte-order marks; and the
README linked a `dev/DIRECTIVES.md` that does not exist. All are fixed.

## Breaking changes

**None.** v0.1.0 exposed no public API; everything in 0.2.0 is new surface.
The removed `serde` feature had no code behind it.

in the configured CI matrix:

run on the conformance grammars by hand, and the differential fuzzer ran
