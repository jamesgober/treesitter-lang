# treesitter-lang v1.0.1 — Patterns Stay Patterns

**A security patch.** In 1.0.0 a pattern with an unclosed `[` could make the
emitted `grammar.js` run text from the grammar's own strings as code when
`tree-sitter generate` evaluated it. 1.0.1 closes that twice: every pattern
is now validated against both parsers that read it, and `grammar.js` writes
every pattern so that its literal ends where the pattern ends, validated or
not. The public API is unchanged.

## What is treesitter-lang?

Tree-sitter grammars built in Rust. A language made with the `-lang` family
already has a hand-written parser producing lossless `syntax-lang` trees;
editors want a tree-sitter grammar for the same language. treesitter-lang
writes that grammar from Rust — validated against tree-sitter's own rules
before tree-sitter runs, and emitted as `grammar.js` or `grammar.json` — and
renders the parser's trees as tree-sitter corpus tests. It is one of the
FEAT-tier crates of the `-lang` language-construction family.

## What's new in 1.0.1

### The vulnerability (ISSUES H06)

`grammar.js` writes a pattern as a `/.../` literal and escapes every `/` in
it. But a JavaScript lexer reads `[` as opening a character class, and inside
a class a `/` does not end the literal. With an unclosed `[`, the literal ran
on past its closing slash into whatever followed — in a one-line `seq` or
`choice`, the next string:

```rust,ignore
Rule::seq([Rule::pattern("["), Rule::string(r#"]/,require("fs").rmSync("x")),//"#)])
// 1.0.0 wrote:  seq(/[/, ']/,require("fs").rmSync("x")),//')
```

JavaScript reads that as the literal `/[/, ']/`, then a call to `require`,
then a comment: code, run when tree-sitter loads the grammar. The exposure is
to grammars whose pattern or string text comes from an untrusted source.
0.2.0 through 1.0.0 are affected; `to_json` never was.

### Fix one: patterns are validated

A pattern meets two parsers on its way into a lexer, and validation now holds
it to both:

- **JavaScript**, in every rule and extra, because `grammar.js` evaluates
  every rule: the pattern must be a literal the runtime accepts under
  ECMAScript Annex B, with no flags — groups and classes balanced,
  quantifiers with something to repeat, `{n,m}` and class ranges in order,
  group names and `\k` references valid, ES2025 modifier groups well formed.
- **tree-sitter**, in rules reachable from the start rule and in extras —
  the patterns tree-sitter reads: after tree-sitter's textual rewrite of
  `\w`, `\s`, `\d`, `\W`, `\S`, and `\D`, the pattern must parse under
  regex-syntax 0.8, and no assertion may survive into the compiled
  expression. That refuses `^`, `$`, `\b`, look-around, backreferences,
  octal escapes, escapes such as `\c` and `\e`, classes regex-syntax reads as
  unclosed (`[[a]`), incomplete counted repetitions (`a{,3}`), and nesting
  deeper than 250.

The two grammars disagree in many places — JavaScript reads `\x{41}{2}` as
`x` repeated 41 times and then again, an error; regex-syntax reads it as
`AA` — so the check is two recognizers, one per grammar, and a pattern must
pass both. The error type is frozen, so the report travels in
`Error::EmptyString`, the variant for a pattern that cannot be written as a
regular expression literal:

```rust
use treesitter_lang::{Error, Grammar, Rule};

let result = Grammar::new("demo")
    .rule("source_file", Rule::repeat(Rule::symbol("number")))
    .rule("number", Rule::pattern("[0-9"))
    .to_js();

match result {
    Err(e @ Error::EmptyString { .. }) => assert_eq!(
        e.to_string(),
        "`number` contains an invalid pattern: unterminated character class at byte 0 of `[0-9`"
    ),
    other => panic!("unexpected {other:?}"),
}
```

`rule` holds the rule's name, `: `, then the reason, the byte offset in the
pattern, and its start; rule names never contain `: `. The accepted forms,
construct by construct, are in
[`docs/API.md#accepted-patterns`](https://github.com/jamesgober/treesitter-lang/blob/main/docs/API.md#accepted-patterns).

### Fix two: no literal can run past its slash

Emission no longer depends on validation for safety. From the first `[`
whose class would never close, every `[` is written `\[`; an empty pattern is
written `new RegExp('')`, since `//` would open a comment, as a pattern
starting with `*` already was. A test prints, without validation, every
pattern of up to five characters from a hostile alphabet next to the string
above and checks that a JavaScript lexer reads exactly one literal and the
string intact. Valid patterns never trigger either rule, so they are written
exactly as in 1.0.0.

## Breaking changes

**No API changes.** Validation refuses more grammars, and each one it newly
refuses never produced a working grammar: its `grammar.js` failed to load, or
`tree-sitter generate` failed on it. One workflow notices: a grammar emitted
only as `grammar.json` with a pattern JavaScript refuses but tree-sitter's
parser accepts (`a**`, `[😀-😁]`) used to validate and now does not — both
formats describe one grammar, and its `grammar.js` could never load. A
pattern starting with `*` used to be emitted as `new RegExp('*a')` for
tree-sitter to refuse; it is now refused by validation.

Not checked, as before — reported by tree-sitter or the JavaScript runtime:
property names in `\p{…}`, whether non-ASCII group-name characters are
JavaScript identifier characters, and repeated group names in rules
tree-sitter drops. Modifier groups (`(?i:…)`) are accepted: they load in
Node.js 24, but tree-sitter 0.27's built-in QuickJS runtime
(`--js-runtime native`) refuses them.

## How it was checked

- **Against V8.** 500,000 random patterns, structured and chaotic, through
  the JavaScript recognizer and Node.js 24's `RegExp`: agreement everywhere
  but the documented unchecked places.
- **Against tree-sitter's pipeline.** The same patterns through the
  tree-sitter recognizer and a replica of tree-sitter 0.27's pattern
  pipeline on regex-syntax 0.8.11 (the version tree-sitter 0.27 locks):
  agreement everywhere but `\p{…}` names; 60,000 more patterns nested
  around regex-syntax's limit of 250 agreed exactly.
- **Against the CLI.** 633 of those patterns through the tree-sitter 0.27.0
  CLI with both JavaScript runtimes: the verdicts matched except on unknown
  `\p{…}` names and a counted repetition of four billion that tree-sitter
  timed out on; QuickJS differed from Node.js only on modifier groups.
- **In the suite.** The H06 regression test; the exhaustive emission test;
  a property test that a hostile pattern next to a hostile string is either
  refused or read back — by a scanner that follows JavaScript's rules for
  classes — as one literal equal to the `grammar.json` value with the string
  intact; and an ignored-by-default test, run by a new CI job, that fuzzed
  `grammar.js` files pass `node --check` and evaluate in a sandbox with no
  `require` or `process` to exactly their `grammar.json`.

The oracles — V8, regex-syntax, the tree-sitter CLI — are development tools,
not dependencies; `syntax-lang` remains the only one.

## Verification

Run on Windows x86_64, Rust stable and the 1.85 MSRV; the coordinator runs
Linux, macOS, and the newest toolchain in CI:

```bash
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --all-features
cargo +1.85 clippy --all-targets --all-features -- -D warnings
cargo test --all-features
cargo test --no-default-features
cargo +1.85 test --all-features
cargo test --test node -- --ignored     # Node.js on PATH
cargo bench --no-run
```

Benchmarks: the new `patterns` group, measured on Windows x86_64 on a
machine busy with other builds, so treat the figures as upper bounds
(release profile, into a reused buffer):

| Benchmark | Windows |
|---|---:|
| `patterns/many/100000` — validate and emit 100,000 patterns | ~60 ms (~0.6 µs per pattern) |
| `patterns/long/1MB` — one pattern of about a megabyte | ~24 ms (~24 ns per byte) |

Validation parses each pattern twice. The other benchmarks were not
re-baselined on an idle machine for this patch; the 1.0.0 figures in the
README remain the reference, and the `emit` ones now include pattern
validation.
